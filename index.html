A command-line tool that turns the HAR file from your browser's Network tab into a folder of JSON mocks. Real responses, one file per endpoint, readable by MSW, connect-api-mocker and Chrome DevTools Local Overrides.

No account, no config file, no signup. Nothing is written unless you give it an output folder, and --dry-run shows every file before it does.

Try it, it writes nothing. 
$ npx har-to-mocks ./your-file.har ./mocks --dry-run

The 30-second workflow

From DevTools to mock server
01

Export a HAR from DevTools

Open the Network tab, use your app, then "Export HAR..." in Chrome or "Save All As HAR" in Firefox. Include content so the responses are in the file.

02

Run har-to-mocks

Filter to the API calls you want, preview the table and the folder tree, then write one JSON file per endpoint.

npx har-to-mocks ./file.har ./mocks --url=/api
03

Point MSW or Chrome at the folder

Load it with mocks-to-msw or connect-api-mocker, or select it in Chrome's Sources → Overrides. The UI now runs on your recorded responses.

Why not hand-write mocks?

Four ways mocks eat your time 01 / 04
01

Hand-written fixtures are slow and wrong

Typing JSON for a 40-field response means typos, missing fields, and shapes that drift from the real API. Recording the real response takes seconds and is exact by definition.

02

The backend is not ready, down, slow, or behind a VPN

Frontend work stalls. Recorded mocks let the UI run fully offline with production-shaped data.

03

Mocks live in several places

One set for dev, another for Storybook, another for tests. har-to-mocks produces one folder of JSON that MSW (dev, Storybook and tests), connect-api-mocker, and Chrome overrides can all read.

04

Reproducing a bug needs the exact response

QA or a teammate exports a HAR from the broken session. You turn it into mocks and replay the exact state locally, or load it as a Chrome override on production without touching code.

Small CLI, careful defaults

Everything below is in v3.0.0 01 / 08
01

Filters

--url substring, --method (GET, POST, PUT, DELETE, PATCH), --type (xhr, fetch, document). Defaults: GET and xhr.

02

Dry run and status column

See create, update or skip per row and the exact folder tree, with [UPDATE] on files that already exist.

03

Interactive picker

-i gives a checkbox list with the focused endpoint's JSON response rendered below it (up to 12 lines), then a confirm step. ↑/↓ navigate, Space toggle, a all, i invert, Enter confirm.

04

--select for scripts and CI

Pick rows by number: --select=1,3,5-7. Interactive mode prints the equivalent value so you can replay the same choice later.

05

Duplicate detection

Requests that share path and method are marked skip, with a hint telling you how to keep the one you want.

06

Two output formats

mocks for MSW and mock servers, chrome-overrides for Chrome DevTools Local Overrides.

07

Friendly errors

File not found, File is not valid JSON, File is not a valid HAR file. Unparsable URLs are skipped with a warning, not a crash.

08

Small bundled install

TypeScript, ES modules, bundled with esbuild into a single small install. Runs on Node.js 22 or newer.

Two output formats, same recording

--format=mocks (default)

Layout is <output>/<url path>/<METHOD>.json. Each file is the raw response body, nothing else: no headers, no status codes. This is the layout mocks-to-msw consumes and connect-api-mocker (Express / webpack-dev-server middleware) serves.

Then do this 
import { createMockHandler } from "mocks-to-msw";
import mocks from "./mocks/mocks";

const { mock } = createMockHandler<keyof typeof mocks>({ mocks, debug: true });

export const handlers = [
  mock.get("/client"),
  mock.post("/client/application", (data) => ({ ...data, modified: true })),
];

mocks-to-msw adds type-safe URL/method pairing, async loading, response modifiers, debug logging, origin configuration, and a CLI that generates a typed import file from the mocks folder.

--format=chrome-overrides

Files are named the way Chrome names them: <host>/<path>, query string kept in the file name, index.html for paths ending in /, special characters escaped, very long URLs in a longurls folder. Binary responses (base64 in the HAR) are decoded, so images and fonts are written as original bytes.

Then do this

In Chrome: Sources → Overrides → Select folder for overrides, pick exactly the folder you wrote to, allow access, reload. Chrome now serves those responses instead of the network, with no code changes to the app at all.

  • Chrome matches by URL only, not method, so a GET and a POST to the same URL share one file (status skip). Different query strings get separate files.
  • Overridden responses come back with status 200 and the real request's headers.
  • A path cannot be both a file and a folder: /api/users and /api/users/1 conflict, and the CLI reports A file and a folder would have the same path.

Who uses it, and for what

Pain · fix · command · format 01 / 10
01

Frontend developer blocked by the backend

format: mocks

The API is not ready, down, or behind a VPN. Record the app once against staging, generate mocks, keep building offline.

npx har-to-mocks ./staging.har ./src/mocks/api --url=/api --dry-run
# then the same command without --dry-run
02

Storybook author

format: mocks

Stories need realistic data. Generate mocks, wire them with mocks-to-msw, reuse the same handlers in the app and in Storybook. The Medium article covers this flow ↗

npx har-to-mocks ./file.har ./mocks --url=/api
03

Component and integration tests

format: mocks

Fixtures nobody updates. Deterministic responses from real traffic instead, served by MSW in Vitest, Jest, React Testing Library, Playwright or Cypress.

npx har-to-mocks ./file.har ./mocks --url=/api --method=GET --method=POST
04

Bug reproduction / QA handoff

format: mocks

QA attaches a HAR to the ticket. Run interactive mode, preview the responses, pick the failing call, replay it.

npx har-to-mocks ./ticket-4821.har ./mocks --interactive
05

Debugging production without a deploy

format: chrome-overrides

Replace any production response with a saved or edited one. Write an overrides folder, select it in DevTools. No proxy, no code change.

npx har-to-mocks ./prod.har ./overrides --format=chrome-overrides
06

Contractor onboarding to an unfamiliar codebase

format: mocks · the author's own story

Day one, no backend access. Record the running app, generate mocks, and have a fully working local frontend before you understand the backend.

npx har-to-mocks ./day-one.har ./src/mocks --url=/api --type=xhr --type=fetch --dry-run
07

Demo and sales environments

format: mocks

Freeze a known-good data set once so demos never depend on a live service.

npx har-to-mocks ./golden-demo.har ./demo/mocks --url=/api
08

Design handoff / prototyping

format: chrome-overrides

Designers and PMs see the UI with real data on a laptop with no backend access.

npx har-to-mocks ./app.har ./overrides --format=chrome-overrides
09

AI-agent workflows

format: mocks

Install the har-extraction skill and ask Claude Code: "Extract mocks from this HAR file for my API tests." Non-interactive flags, deterministic output, dry run and readable tables make the CLI agent-friendly.

npx skills add peterknezek/skills
10

REST query variants

format: mocks or chrome-overrides

?page=1 and ?page=2 hit the same path. The Query column plus --select or interactive mode let you keep the one you mean; chrome-overrides keeps both as separate files.

npx har-to-mocks ./file.har ./mocks --url=?page= --select=2

Questions developers ask first

Including what it does not do yet
Q1

Will it overwrite my files?

Not silently. Without an output folder nothing is written. With one, the Status column tells you what will be created, updated or skipped, --dry-run shows the full tree first, and interactive mode asks for confirmation.

Q2

My HAR has 600 entries.

Narrow it with --url, --method and --type, then pick rows with the interactive picker or --select=1,3,5-7.

Q3

I use GraphQL.

Requests are keyed by URL path and method, so multiple GraphQL operations on one endpoint collide today (open issue #12). Interactive mode and --select let you pick which one to keep. Operation splitting is not implemented.

Q4

Same endpoint, different query params?

The Query column shows them apart. The chrome-overrides format writes separate files per query string; in the mocks format use --select or interactive mode to choose. Automatic handling is tracked in open issue #18.

Q5

Why don't I see my fetch requests?

The default resource type is xhr and the default method is GET. Pass --type=fetch (and --method=POST etc.) to include them. --url is a case-sensitive substring match, not a regex.

Q6

Does it leak secrets?

HAR files can contain cookies and tokens. The mocks keep response bodies only, no headers. Still, review the output before committing it.
